## 为什么需要了解多种 ID 格式？

在分布式系统、数据库主键设计、日志追踪等场景中，"生成唯一标识符"是每个开发者都会遇到的基础需求。但唯一 ID 并非只有 UUID v4 一种选择。

不同的 ID 格式在长度、排序性、可读性、生成速度和存储效率上差异显著。选错了格式，可能在数据库百万级数据后才发现索引碎片化严重、查询变慢。

## 主流 ID 格式速览

| 格式 | 长度 | 排序性 | 生成速度 | 适用场景 |
|------|------|--------|----------|----------|
| UUID v4 | 36 字符 | ❌ 无 | 快 | 通用唯一标识 |
| UUID v7 | 36 字符 | ✅ 时间 | 快 | 数据库主键 |
| ULID | 26 字符 | ✅ 时间 | 快 | 可排序的短ID |
| NanoID | 21 字符 | ❌ 无 | 极快 | 短链接、URL |
| CUID | ~25 字符 | ✅ 水平 | 快 | 多进程 ID |
| Snowflake | 19 位数字 | ✅ 时间 | 快 | 分布式 ID |

## 各格式详解

### UUID — 久经考验的标准

UUID（Universally Unique Identifier）是 128 位标识符的国际标准（RFC 4122）。最常用的是 v4（完全随机）和 v7（基于时间戳+随机）。

**优点：**
- 广泛支持，几乎所有语言都有标准库
- 碰撞概率极低
- v7 版本可按生成时间排序，适合 B-tree 索引

**缺点：**
- 36 个字符（含连字符），存储较贵
- v4 完全随机，B-tree 索引容易碎片化

### ULID — 短而有序的替代品

ULID（Universally Unique Lexicographically Sortable Identifier）是 128 位的压缩编码标识符，使用 Crockford 的 Base32 编码（不含 I、L、O、U，避免混淆）。

**ULID 的典型形态：** `01ARZ3NDEKTSV4RRFFQ69G5FAV`
- 前 10 个字符：毫秒级时间戳（Base32 编码）
- 后 16 个字符：随机

**关键优势：**
- 只有 26 个字符，比 UUID 短 28%
- 字典序排序即等于时间排序
- 不包含敏感字符，可安全用于 URL 和文件名
- 可转化为 UUID 格式

### NanoID — 为现代 Web 而生

NanoID 不是 128 位标准，而是一个可自定义长度和字母表的紧凑 ID 生成器。默认 21 字符，使用 URL 安全的 A-Za-z0-9_- 字母表。

**NanoID 的优势：**
- 仅 21 字符，极其紧凑
- 生成速度极快（比 UUID 快 60%）
- URL 安全，无特殊字符
- 可自定义长度满足碰撞概率要求

## 如何选择？

### 场景 1：用户 ID 或通用标识 → UUID v4
如果只是需要一个"很不可能重复"的 ID，且不关心排序，UUID v4 是最安全的选择。

### 场景 2：数据库主键 → UUID v7 或 ULID
数据库主键需要按顺序插入以保持 B-tree 索引效率。UUID v7 和 ULID 都支持时间排序。
- **用 MySQL/PostgreSQL 的 UUID 类型** → 选 UUID v7
- **需要更短的 ID** → 选 ULID（26 字符 vs 36 字符）
- **需要存为 bigint** → 选 Snowflake（64 位整数）

### 场景 3：短链接 / URL 友好 → NanoID
只需要 8-14 字符就能达到可接受的碰撞概率，而且 URL 安全不需要编码。

### 场景 4：水平扩展多节点 → CUID 或 Snowflake
当 ID 生成器需要在多个进程或节点上运行时，CUID（包含主机指纹）和 Snowflake（包含工作节点 ID）都能避免跨节点冲突。

## 总结

| 你的需求 | 推荐格式 |
|----------|----------|
| 只要一个唯一 ID | UUID v4 |
| 需要数据库主键 | UUID v7 或 ULID |
| 要最短的 ID | NanoID |
| 需要整数主键 | Snowflake |
| 多节点生成 | CUID 或 Snowflake |

没有万能的 ID 格式，只有最适合你的场景的那一个。
